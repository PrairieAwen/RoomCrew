AGENT FOUNDATION / 01

先统一抽象：User、通用 Agent、独立 Run、安全 VM

推荐方案：以通用 AgentKernel 包装 Deep Agents；助手与员工仅使用不同配置。每项任务创建独立 AgentRun / Thread / 协程 / 轨迹。多 Agent 层负责意图识别、能力路由和任务协调。首版本地使用 SQLite + AsyncSqliteSaver + 文件目录。
概念本版定义与上一版的修正
老板User，人类请求与审批主体不进入 AgentDefinition，不占模型运行名额
助手普通 AgentDefinition 的一种配置，承担理解、路由或汇总不建立特殊 Assistant 执行内核，也可选择自己完成任务
员工其他可配置的 AgentDefinition与助手共用同一构造、运行、中间件和记录机制
监管员安全 VM 及其 Policy / Credential 服务的应用映射不创建一个拥有签发权的 LLM Agent
同一个 Agent 并发工作同一配置产生多个独立 Run取消“一名员工只能有一个活跃 Run”的默认限制
执行方式本地异步协程优先，单 Run 单执行者不把每个 Agent / Run 都先拆成独立进程
持久化产品轨迹独立保存，框架检查点可选 SQLiteDeep Agents SDK 不强制 PostgreSQL；框架检查点不等于产品轨迹

本文为 v0.3 完整调度设计建议，在同一文件替代 v0.1，不保留并列旧方案。已确认的 User / Agent / 安全 VM 抽象按用户补充落实；其余实现与参数待评审。本次不编写业务代码、不调用真实模型或启动 VM。

“两个不同人物都派发给某个 Agent”同时兼容两种理解：不同任务交给同一 Agent 时有独立 Run；若不同人物形象复用同一配置，可附可选 display_binding_id 分组展示，它不决定权限或上下文。

AGENT FOUNDATION / 02

总体结构：通用内核在下，路由与协作在上

  • 基础层：配置解析、RunContext、模型 / 工具适配、Skills、压缩、轨迹、中断和 checkpoint。所有 Agent 共用。
  • 应用层：助手理解任务、查候选能力、生成 RouteDecision；确定性调度器创建 Task / Run 并协调结果。
  • 安全层：User 的可信决定、安全 VM 的权限和凭据服务、隔离执行网关。角色提示词不能替代它。
  • 数据层：每工作空间业务 SQLite、框架 checkpoint SQLite、受控文件目录；异步请求并发，数据库短事务串行。
AGENT FOUNDATION / 03

对象模型与 ID：配置可复用，执行必须独立

对象 / ID含义与生命周期隔离或版本规则
User / user_id人类用户，权限与审批主体由可信入口绑定，不能由模型自行填写
AgentDefinition / agent_id名称、说明、能力、模型、工具、Skills、上下文策略、并发上限长期可配置；助手与员工结构相同
AgentConfigRevision / config_revision一份不可变的有效配置运行开始固定版本；修改只影响新 Run，安全撤销仍即时检查
UserRequest / request_id一次用户输入或请求组可产生一个或多个任务；用于把子轨迹汇总回同一次请求
Conversation / conversation_id应用层对话与展示容器不直接等于框架 thread，不在并发任务之间共享运行历史
Task / task_id要完成的工作及验收标准包含输入来源、依赖和父任务，可有多个尝试
AgentRun / run_id某任务的一次独立执行绑定 agent_id + 配置快照 + Task；一项新任务新建 Run
Runtime thread / thread_id框架 checkpoint 的会话键首版一 Run 一 thread；恢复用原键，不让两个活跃 Run 共用
ExecutionLease / epoch当前实际执行者与接管版本同 Run 只能有一个执行协程；恢复要拒绝迟到的旧执行者
DisplayBinding / display_binding_id可选的人物展示或指派来源引用只用于应用分组；不作为 Agent 身份或权限依据
AgentDefinition: agent-general
  ├─ Task A → Run A → Thread A → Trace A
  └─ Task B → Run B → Thread B → Trace B

同配置复用的是定义，不是消息列表、scratch、middleware 状态或 checkpoint thread。

Agent 配置至少说明：模型引用、角色提示词版本、允许工具、skill IDs / 版本、记忆范围、上下文预算、max_concurrent_runs、超时和请求额度。默认助手也由同一 AgentFactory 创建，区别仅在配置与可用工具。

一个 Run 创建一套有状态 middleware 与运行图实例。可缓存不可变配置、只读技能包和已验证安全的连接资源，不能把正在使用的消息数组、middleware 字段或可变后端对象当成全局单例。
AGENT FOUNDATION / 05

本地模型配置与可信 ModelFactory：Agent 只拿可用接口

本次确认的边界：模型底层配置由 User 在本地可信入口管理，运行时的 ModelFactory 按引用解析。真实厂商配置与密钥不放入 prompt、Agent 状态、checkpoint、普通轨迹或可访问文件工具；生产秘密由安全 VM 的连接器使用。

这里区分 LLM 的可见上下文与运行程序的权限。LLM 只能经应用输入、工具输出和观测接触配置；若给它与可信服务同权限的任意宿主代码，则普通文件权限、隐藏目录或 DPAPI 并不能可靠隔开两者。因此配置私有化必须与受控工具面、独立安全域一起实现。

本地管理入口可以是后续设置界面或可信命令行；它读取 / 修改的控制域不在 Agent 的 read_file、Skill source、导入目录或执行 VM 挂载范围。必要时将配置导入安全 VM 的私有卷；不为编辑方便把整份配置复制到项目或 Agent 工作区。

模型创建与调用流程

  • 1、User 本地配置模型参数，密钥经可信输入单独写入凭据服务；ConfigService 做 schema、允许的适配器、端点和字段校验后原子发布新版本。配置文件不执行任意 Python、动态 import 或表达式。
  • 2、创建 Run 时，AgentFactory 从可信 AgentConfigRevision 取 profile_ref。profile_ref 不能由模型临时给出的文件路径或 URL 替换。
  • 3、可信 ModelFactory 请求 Broker 解析配置并建立绑定；Broker 校验 workspace、Run、epoch、预算、端点与凭据范围。
  • 4、安全域内连接器创建真实 provider SDK 客户端；主机 Run 获得受限 BaseChatModel 代理 / 句柄，而非原始配置或 Key。
  • 5、通用 AgentKernel 将预先构造的代理实例传给 create_deep_agent(model=...)。初始化、摘要、路由和复核全部使用受控入口。
  • 6、每次推理由连接器添加认证信息并请求固定端点，模型看到的输入不包含认证头。返回时只转换获准消息、工具调用、用量和错误状态。
  • 7、暂停 / 重启只持久保存绑定引用。恢复时重新授权并创建运行客户端，不从 checkpoint 反序列化含密钥的 SDK 对象。

Deep Agents 支持传入已初始化的模型实例，因此无需让模型自己生成初始化代码或读配置文件。将模型实例做成安全代理还需要验证 streaming、bind_tools、model profile、计量、摘要和异常转换的兼容性；本页只给出设计。官方 model 参数说明

“Agent 无感知”具体保证什么

通道必须采取的限制
Prompt / 消息 / graph state不注入底层参数和秘密；RunContext 仅保留引用，配置不是可序列化给模型的对象
文件、Skills、MCP、脚本配置目录不列入获准视图；绝对路径、遍历、重解析点和别名不能旁路；脚本仅进隔离 VM
模型元数据 / 回调真实模型名、端点、请求对象和 provider response_metadata 按白名单处理，不整体回流给 Agent
轨迹 / checkpoint / 导出只存 profile / binding 引用与必要用量；不 dump config / client / Authorization；序列化和调试链路分别检查
错误 / 调试 / tracing不直接 str(exception) 回传 SDK 错误正文、URL 或认证字段；返回稳定错误码，外发 tracing 默认关闭
管理入口与代理接口修改配置、测试凭据、导出配置属于可信 User 通道；推理代理不提供 get_secret / read_config 等能力
环境变量主机 Agent 运行不使用全局 .env / 系统 API Key 自动兜底；连接器显式传入配置，执行 VM 不继承这些秘密

厂商继续会话必需的签名、私有状态或 opaque items 由连接器按 Run 保存和回放，不作为 Agent 可读配置公开。代理不能简单丢弃这些内容；工具调用、流式、摘要、计量和恢复需要逐厂商验证。

这里保证的是应用不通过数据面向模型公开配置。模型可能根据能力或输出风格推测服务来源，不能承诺它永远无法猜测厂商。对模型身份保密也不能代替 Key 和账号权限保护。

加密文件、并发和配置更新

  • 加密文件解决落盘保护，工具访问控制与安全域解决谁能使用。Windows 宿主需要封装本地秘密或卷解锁材料时可评估 CurrentUser DPAPI；同用户进程的解密能力并不因它自动消失，VM 内存储按其平台设计。
  • 同一 profile 可供多个 Run 使用，绑定、额度、请求和轨迹各自独立；SDK 客户端不得用可变全局参数在并发运行之间切换配置。
  • 模型 / 端点 / 数据策略变更产生新配置版本，新 Run 采用新版本；在途 Run 不静默更换厂商或 base_url。
  • 同一逻辑凭据在相同账号 / 端点范围内轮换时，由 Broker 验证并刷新连接器客户端；撤销立即阻止后续请求，不承诺撤回已发出的远端请求。
  • 端点 origin 改变时不自动携带旧凭据；经过可信配置流程重新绑定，跨 origin 重定向也不能转发认证。
  • 缺少、锁定或失效的配置进入配置待处理状态，通知 User 修复；不要求模型索取 Key，不自动搜索 .env 或普通文件。

Microsoft CryptProtectData 说明 DPAPI 通常绑定相同登录凭据和计算机；它不能被解释为对同一用户所有进程的强隔离。

AGENT FOUNDATION / 06

同一个 Agent 同时接两项任务

  • 调度器为每 Run 建立一个 asyncio task，使用独立图实例、RunContext、thread_id、消息状态和文件命名空间。
  • 同一 Agent 是否可并行取决于配置额度，不默认锁成 1。建议首轮全局活跃模型请求 2、每 Agent 活跃 Run 上限 2，均可配置并需测量。
  • 资源分层限制：全局 / workspace / agent / provider / 工具资源。队列超过额度时等待，不通过新增协程绕开预算。
  • SQLite 写锁只覆盖短写入，不锁住整个 graph.ainvoke；模型等待期间其他 Run 可以推进。
  • 相同 thread 的恢复必须串行；两个不同任务不能因同属一个 agent_id 而误用同一 thread。
  • 非异步 CPU 工作放有界执行器；任意用户代码进入执行 VM。异步协程隔离的是运行状态，不是 OS 安全边界。
  • profile 注册等全局配置在启动时冻结，禁止为不同并发 Run 修改全局 registry；运行差异通过实例参数与只读视图传递。

AGENT FOUNDATION / 08

轨迹写入与查询：先落库，再发布持久事件

  • 生命周期、工具意图 / 收据、用户决定和关键产物事件及时提交；数据库无法可靠写入时停止新副作用分发。
  • Token 片段不逐个 commit。可按有界批次持久化；若采用纯临时显示通道，应明确标注未提交，最终消息仍可靠落库。
  • 持久事件只在数据库 commit 后对外发布，断线通过 workspace_seq 补齐；重复事件用 event_id 去重。
  • 查询接口提供 list_runs(agent_id, task_id, status)、get_run(run_id)、list_run_events(run_id, after_seq)、subscribe_events(workspace, after_seq)。
  • 应用按 Agent 汇总“多条轨迹”，点进一条 Run 看其消息、工具、Skills 和压缩过程；不把两个 Run 合并成一段会话。
  • checkpoint 不作为应用唯一轨迹来源。不同框架版本、摘要策略或检查点清理，都不能让已保存的产品历史消失。
AGENT FOUNDATION / 09

本地持久化选型：SQLite，不要求安装 PostgreSQL

Deep Agents 建立在 LangGraph 上，运行持久化由注入的 checkpointer 决定。SDK 可以使用内存、SQLite 或 PostgreSQL 等实现；不传持久 checkpointer 就不能把重启恢复视为已具备。托管部署的数据库选择不等于 SDK 强制依赖。官方持久化说明

本次已读取安装版本的 AsyncSqliteSaver：使用 asyncio.Lock，初始化开启 WAL，提供异步读写方法。这说明可以采用异步 SQLite 适配；真实负载、故障恢复和磁盘策略仍需验证。
  • CheckpointManager 在每个工作空间生命周期内维护一个 AsyncSqliteSaver / aiosqlite 连接，多个独立 thread 的短检查点操作受锁协调；不要每个 Run 结束就关闭别人仍在用的连接。
  • 产品业务库由独立异步写队列处理；框架库由 saver 管理。两者没有跨库原子事务，依靠操作收据与恢复对账补齐窗口。
  • WAL 支持读写并行，但仍是单写入者；设置 busy timeout、外键和事务长度，不把模型推理放进数据库事务。
  • 数据库放本机受控文件系统，不放网络共享目录；备份使用一致性快照，不能忽略 WAL。
  • SQLite 是个人桌面的工程建议，不是无限并发承诺。未来出现多主机服务或持续写争用再考虑数据库升级。

SQLite 应用场景 · WAL 与并发限制

首版本地同一数据根由一个 RuntimeHost 管理，多个调用方共享该服务。AsyncSqliteSaver 的 asyncio.Lock 只协调本进程，不能据此宣称跨进程调度安全；进入多进程或多主机前需补租约、接管与存储验证。

上下文超限：中间件压缩，最终请求再验长度

  • 1、从模型配置取真实可用窗口 C，计算输入 I、输出 / reasoning 预留 R 与安全余量 M。要求 I + R + M ≤ C；不知道上限时要求有效配置，不猜固定 128K。

恢复、轨迹与工具副作用的一致性

  • 业务库中的 Run 状态 / 事件与 runtime.sqlite checkpoint 不构成跨库原子事务。事件缺口、终态通知丢失和 checkpoint 滞后都需要恢复核对。

  • 操作状态包括 PREPARED、WAITING_APPROVAL、READY、DISPATCHING、SUCCEEDED、FAILED_KNOWN、UNKNOWN_EFFECT；分发后失联进入对账。
  • 模型生成新的 tool_call_id 不自动表示新的业务副作用意图。重复发送 / 提交必须由稳定的 action_ref 与产品幂等规则约束。
  • 恢复使用原 thread 和固定配置；旧执行者未确认停止或在途外部操作未核对时，不并发接管同一 Run。
  • 持久轨迹引用的大结果必须落到受控内容存储，不能只指向稍后会删除的 scratch。清理先检查引用与保留策略。
  • 保存 Deep Agents、LangGraph、图结构、schema、模型与技能版本；升级不能强行读取未知 checkpoint，也不从不可信文件导入可执行序列化对象。

相同错误反复出现记录输入版本、错误码、工具参数与产物 hash 的进展指纹；无新证据达到限额就请求有效决策
模型说完成但产物不足结果提议经过产物 / 证据校验，Task 成功独立判断
换模型 / 换厂商用能力矩阵验证工具、结构化输出、上下文和计量；新 Run 使用业务事实，不搬不透明私有状态
请求取消后仍可能计费保留预算预留与已知调用记录，不能把本地取消当服务端请求撤回

所有请求，包括助手路由、执行、压缩和复核，都进入同一计量体系。初始可设置同一网络请求最多 2 次尝试、同一边界最多 2 轮压缩修复、有限返工；具体上限按端点与任务评估，不能各层重置形成放大。

端口用途与合同

一次请求包含两项不同任务
1. UserRequest R：任务 A 与任务 B
2. 助手路由 Run P：读取允许的 Agent / Skill 摘要
3. RouteDecision：A → agent-X；B → agent-X（合法）

编号测试情景必须成立
